Local models as a personal agent's backend

How well does a local model serve a personal agent on a Mac? Three suites measure it under fixed, versioned settings (the memory suite is still being built), so a new model or quantization lands next to the ones already measured, and anyone with an Apple-silicon Mac can rerun the backend's speed and capability legs.

Backend

What an agent waits for: time to first token with a cached or a cold prompt, decode speed from 16K to 110K tokens of context, a 20-step agent trajectory, and the server's memory. Plus a functional gate, and tool-call accuracy (shown with agent ability).

Agent ability

Whether agents built on the model get work done. The same tasks, with byte-identical prompts, run through Claude Code, Hermes Agent and localmelo, and objective checkers score them.

Memory

Whether an agent keeps a correct, current and compact memory. A synthetic 10-day timeline is fed to the agent one session a day, and a fixed reader then answers 60 questions from the memory store alone. The reader and the scoring are built; the session runner is next.

How it works

Each suite drives a model through the same pieces. The arrows follow the model calls and, at the bottom, the results.

  • One recorder proxy for every harnessEvery model call of an agent harness, and every T4 reader call, goes through bench/proxy. It counts agent steps and model time the same way for Claude Code, Hermes Agent and localmelo, sets the thinking setting, and gives the harnesses' requests the model's recommended sampling. The backend's speed probes call the server directly, with the same sampling, so their timings carry no proxy overhead.
  • Fixed, versioned protocolsTasks, budgets, the sampling rule, thinking (off in the main arm) and server settings are fixed per protocol. Every result names its protocol and machine, and no table mixes them.
  • Quiet machine for timed workThe backend's timed units wait until other processes' CPU and GPU load is below fixed thresholds and the battery is high enough. A unit with a major disturbance is repeated, up to 3 attempts; a minor one is kept and flagged.
  • Recorded resultsEach result records the macOS and Xcode builds, the server version and the machine. A backend run publishes its manifest and the speed leg's raw records (timings, machine samples, and the model's output on synthetic prompts); the capability leg publishes only allowlisted files (per-call metrics and checker output, no request or response bodies). Agent transcripts, harness homes and server logs stay on the machine.

Suites

Backend

eval/backend
One run
Once the checkpoint is prepared (download, convert, register), one command per model starts the server with the fixed settings and runs the speed leg, then the capability leg on the same server launch. modeleval publish writes the rows.
Speed leg
Time to first token on a cached ~15K-token agent prefix and on a cold 64K-token prompt; decode speed at 16K, 32K, 64K and 110K tokens of context; a 20-step agent trajectory; peak server memory. Before the timed units, an untimed functional gate and 22 tool-call cases (shown in the Agent ability table).
Capability leg
The agent_ability tasks through all three harnesses, one run each, with a budget of 30 agent steps (successful model calls that carry tools), 40 harness turns and 3600 s per task. A gate set first (12 Aider exercises and 10 MCPMark tasks); the ranking set (the other 22 Aider Python exercises) runs unless the gate finds the model worse than the reference. The decision rules are fixed in advance: the gate calls a model worse only when it loses at least 5 more tasks than it wins, consistently in at least two harnesses; the ranking set calls it better or worse only at sign-test p < 0.05 over tasks.

eval/memory
T4 timeline
86 synthetic messages, emails and calendar entries over 10 days, with updates, relative dates, facts that only combine across days, and distractors.
Probes
60 questions, 12 each: extraction, cross-session, temporal, knowledge update, abstention. A fixed reader answers them from the memory store alone, with thinking off and temperature 0.
Store checks
Fabricated sources, source precision, duplicates and the store's size in tokens.
Status
Fixtures, the pab MCP server, the reader and the oracle are built; the reader answers 48/48 answerable and 12/12 abstention probes from the ideal store. The runner that drives the harnesses through the 10 days comes next.

Run it on your Mac

You need an Apple-silicon Mac, uv, and an oMLX 0.7.1rc1 checkout (commit 7a5a3d75) with its own .venv, the protocol's server. The capability leg also needs the three harnesses, at the versions in eval/backend/pins.toml, and the pinned task data (eval/agent_ability). eval/backend/README.md has the details.

git clone https://github.com/xthomaswang/personal_agent_eval_pipeline.git
cd personal_agent_eval_pipeline/eval/backend
# once per Mac: put the paths that differ from config.defaults.toml in config.toml
uv sync
uv sync --project envs/capability && uv sync --project envs/agent-tools
uv run modeleval selftest       # offline; prints the resolved paths, a FAIL names what is missing
# once per model: add it to models.toml, then prepare its checkpoint
uv run modeleval download <model> && uv run modeleval convert <model>   # it has a prepare entry
uv run modeleval register <model>   # or: its checkpoint is already at its models.toml path
(cd harness && uv run agentbench fixtures build)   # once: the speed prompts (Qwen3.8 tokenizer)
uv run modeleval plan <model>
uv run modeleval run <model>    # speed leg + capability leg
uv run modeleval publish        # rows under docs/benchmark/<machine>/...
cd ../.. && python3 scripts/build_docs.py   # rebuild this page

On a new machine, run the reference model (Qwen3.8-27B oQ5 + MTP) first, so that every other model has something to be compared with. Three steps are not in these commands:

  • The reference model has no prepare entry: download Qwen/Qwen3.8-27B at the revision in models.toml, convert it at oQ level 5 with eval/backend/scripts/oq_convert.py (its docstring has the command), then register it. The fixture build reads its tokenizer: set AGENTBENCH_TOKENIZER_DIR to the checkpoint unless it is under ~/Developer/mlsys/models/oq/.
  • The capability leg's harness epoch includes the workspace path and the agent configs under [paths] agent_root, so on another Mac run refuses with the epoch id your inputs hash to. Check the difference, then write that id into eval/backend/pins.toml (its header explains epochs).
  • publish writes rows only under a known protocol: a different macOS or Xcode build, or a different harness epoch, first needs its own protocol id in eval/backend/src/modeleval/publish.py; otherwise the run is skipped.
